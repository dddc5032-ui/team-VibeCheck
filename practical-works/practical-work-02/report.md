## 4 Порядок работы с репозиторием

Команда работала с репозиторием через веб-интерфейс GitHub (`github.com`), без установки Git на локальный компьютер. При таком способе клонировать репозиторий и отправлять изменения командой `push` не нужно: все изменения сразу сохраняются в удалённом репозитории.

Каждый участник команды выполнил одну и ту же последовательность действий:  
1. **Создание своей ветки:** На странице репозитория участник открывает список веток, вводит имя новой ветки и создаёт её от основной ветки `main`. Шаблон имени ветки: `feature/<имя_участника>` или `role/<название_роли>`.  
2. **Внесение изменений:** В своей ветке участник открывает нужный файл, нажимает кнопку редактирования (значок карандаша) и изменяет текст по своей роли. Новый файл создаётся через меню «Add file».  
3. **Коммит:** Изменения сохраняются кнопкой «Commit changes». В сообщении коммита коротко указывается суть изменения, например: `docs: дополнил описание своей роли`.  
4. **Создание Pull Request:** На вкладке «Pull requests» участник создаёт Pull Request для слияния своей ветки с основной веткой `main`.  
5. **Ревью:** Проверяющий открывает Pull Request, просматривает изменения на вкладке «Files changed», оставляет замечания и одобряет изменения.  
6. **Слияние:** После одобрения ветка сливается с основной кнопкой «Merge pull request».

## 6 Pull Request и ревью

Изменения попадают в основную ветку `main` только через Pull Request. Каждый участник создаёт Pull Request из своей ветки. Изменения проверяет ведущий разработчик Кареев Н.А.: просматривает изменённые файлы, оставляет замечания и после их исправления одобряет слияние. Pull Request самого ведущего разработчика проверяет другой участник команды.

## 7 Вывод

В ходе самостоятельной работы № 2 команда зарегистрировалась на GitHub, создала командный репозиторий и через веб-интерфейс GitHub отработала полный цикл работы с системой контроля версий: создание веток, коммиты, Pull Request, ревью и слияние.
